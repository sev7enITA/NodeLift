											217 text 2606.25091v2 proves with closed-form inequalities exactly the thing your design must survive:  if the server can host both models, co-located speculative decoding (your B1) has lower latency and communication than synchronous distributed SD (your D1), at the same per-output FLOPs and memory.  Their stated exception regime — pipelined DSD competitive only when RTT is small relative to the edge drafting window — is where you live at the  median  (6–9 ms) but not at your  p95  (68–80 ms), which already exceeds the ~50 ms RTT bound below which the DSD literature finds distributed execution ever winning. So your design review must be organized around three honest propositions:

												234 text "Exact greedy" is not bitwise-exact in current llama.cpp, and upstream says so. docs/speculative.md  states that stochastic CPU and backend sampling can select different tokens because floating-point ops differ between implementations/devices, and instructs using greedy when exact matching is required. Worse, this is not hypothetical: issue #25618 (draft-mtp / draft-dspark, temperature 0, top_k 1, repeat_penalty 1.0) documents vanilla-vs-speculative divergence that  flipped with V-cache quantization  (Q8_0 KV diverged, one F16 control was byte-exact) and flash-attention on/off, with endpoint/sampler interaction not fully excluded; issue #27975 (Aug 2026) reports an external DFlash drafter changing temp-0 outputs. Your "batch/single drift must be measured" is therefore not a nice-to-have:  the drift sweep must include batch width {1..17}, thread count, flash-attn on/off, KV cache type {F16, Q8_0}, CPU governor state, and the exact server endpoint/sampler path , with the llama.cpp commit hash recorded (defaults have drifted upstream mid-2026 — #25908 shows  --spec-draft-p-min  default changed via #23269). Add a runtime canary: periodically shadow-replay committed tokens through the host-only path; on mismatch, feature-flag the spec path off and log it.

												237 text Sampler/verifier state must be locked, not just "greedy".  Pure argmax means temp=0  and  repeat/frequency/presence penalties off  and  no logit bias  and  top_k=1  and  min_p=0  and  no grammar constraints. 										278 heading 3. The break-even you must publish before any speedup claim, Value: 2
											279 text 3. The break-even you must publish before any speedup claim
										280 container
											281 text Win condition for D1 over B0, per round:  a / r_h > k / r_d + T_net + T_v + T_sync , where  a  = expected committed tokens per round (≤ k+1),  r_h  = host-only target rate,  r_d  = phone draft rate,  k  = block size. Rearranged:  r_h < (a/k)·r_d / (1 + (T_net + T_v)·r_d / k) . With your measured T_net (8 ms median, 75 ms p95) network is  not  the binding term;  k/r_d  — 16 sequential phone forwards — is. So for k=16, a≈4, break-even needs the host-only target to be roughly 4× slower per token than the 0.5B phone draft. Corollaries: (i) the Qwen2.5-0.5B/1.5B pair can only ever be a correctness qualification — agree with your framing, and say so in every report; (ii) the latency case lives or dies on the large-target arm and on measured  a ; (iii) D2 (pipelined/async) is the only latency hope per 2606.25091's analysis, and it carries a correctness coupling you didn't state:  greedy verification forbids drafting round n+1 before round n's commits are known, so remote async requires assumed-acceptance chains whose rejections are pure waste.  Label D2 accordingly.
