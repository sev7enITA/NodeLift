											383 text llama_memory_seq_rm
											384 text  treated as failure → spurious full reset and full re-prefill.  HIGH, proven (performance; correctness preserved).
 sync  calls  llama_memory_seq_rm(...,0,int(keep),-1)  unconditionally and treats a return of 0 as failure ( {reset();keep=0;} ). But 0 is also the legitimate "nothing to remove" return when  keep == cached.size() , i.e. when the cache is already a strict prefix of the requested prefix. Trigger:  every all-accepted block on a draft engine. draft  leaves  cached = prefix + proposal ; verify then commits  proposal + bonus ; the next  draft(prefix+proposal+bonus)  computes LCP  keep = |cached| , no decrement fires ( keep<cached.size()  false,  keep==prefix.size()  false,  next  non-empty), the removal range is empty, returns 0 →  reset()  → the entire prefix is re-decoded from position 0. Over a generation this is O(L²) extra draft-model compute; the best acceptance outcome becomes the slowest round, and  draft_ms / prefill ms  grow with prefix length, corrupting your latency attribution. Today this bites  local_draft  on the host; it will equally bite the phone once the JNI app ships this core (phone impact is extrapolated — native phone performance is unmeasured, per your note). The same misfire fires harmlessly on every engine's first prefill after load (empty cache → 0 removed → reset), which confirms the branch is live. Note  verify()  already has the correct guard ( if(keep<cached.size()) ) —  sync  is missing it.  Minimal fix:  mirror verify's structure — only invoke/treat-as-failure when  keep<cached.size() ; in the skip case the existing  next  stays valid (logits after  cached.back() ) and the delta decode refreshes it.
