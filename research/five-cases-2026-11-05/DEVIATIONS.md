# Protocol deviations and follow-ups

The frozen `PLAN.md` and prompt hashes remain unchanged.

1. **Browser review timing:** the initial free API reviews preceded inference, but Gemini and GLM browser access was disrupted by concurrent browser work. The user later made Vivaldi available. Their new reviews were acquired after the local measurements and included those outcomes. This is a results-informed static review, not blinded prereview or independent replication. No timed MLX inference overlapped the agent's browser review actions. Kimi returned a capacity refusal; Gemma returned two rate limits.
2. **Numerical follow-ups:** after the planned 2x2 history/current-width trace, the investigation added attention-projection input capture and one isolated identical-row width-one/width-four projection probe. These localize a discrepancy on the same diagnostic prefix; they are not new qualification data or evidence of a complete fix.
3. **Retained harness failures:** the first localization process used an unsupported MLX array `.copy()` method and failed; the replacement used the supported array constructor. A follow-up initially pointed to an already existing evidence directory and refused overwriting it. Original failed sources, logs and exit status are retained. Both successful reruns use distinct monitor directories.
4. **Readiness export correction:** public readiness initially used an inappropriate `is not None` check on a boolean. It was corrected to `bool(selected_ready_node)` before remote publication. Local raw snapshots always recorded `false`. Additions after the user reopened the phone remain separate snapshots; no historical ready capability is treated as a live connection.
5. **Bounded physical wait:** after the user offered the Xiaomi, a separate two-minute readiness window was prepared. A paced transport job can run only following fresh online telemetry. No available node means no physical test, not zero transport cost. The current Wi-Fi topology is not independently re-established in this cycle.
