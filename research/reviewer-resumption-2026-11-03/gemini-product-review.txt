Finding 9 — Non-integer browser downscaling (532px to 460px) of a dense Version 27 QR code introduces sub-pixel interpolation blur

Severity: Low

File / Function: docs/evidence/qr-pairing-2026-11-01/review-adjudication.md (Bullet: Optical density)

Concrete Trigger & Evidence: The protocol uses QR Version 27 (125 modules per side) with a 4-module quiet zone (125 + 2 × 4 = 133 total modules per side) rendered on a 532px native canvas (532 / 133 = 4.0 px/module exact integer alignment), which is then scaled to 460px in the browser (460 / 133 ≈ 3.4586 px/module). Scaling 133 modules to 460px places almost every module edge on a fractional pixel boundary, causing browser bilinear resampling to blur black/white transitions across all 125×125 modules, while physical camera scanning on hardware remains unmeasured.

Smallest Fix: Render the QR element in the browser at an exact integer multiple of 133px (399px for 3 px/module or 532px for 4 px/module) with CSS image-rendering: pixelated / crisp-edges.

Meaningful Test: Automated DOM/CSS check asserting canvas.clientWidth % 133 === 0 (on 1x DPR) and getComputedStyle(canvas).imageRendering === 'pixelated'.

Finding 11 — Backward clock adjustment (now < lastSuccess) combined with a failed update check causes UpdatePolicy.due to trigger an immediate retry on every onResume

Severity: High

File / Function: apps/android/app/src/main/java/dev/nodelift/companion/UpdatePolicy.kt:UpdatePolicy.due, apps/android/app/src/main/java/dev/nodelift/companion/UpdateMonitor.kt:onResume & check, apps/ios/NodeLift/UpdateMonitor.swift:onResume & check

Concrete Trigger & Evidence: In UpdatePolicy.kt:UpdatePolicy.due:

Kotlin
fun due(now:Long,lastSuccess:Long,lastAttempt:Long):Boolean {
    if(now<lastSuccess || now<lastAttempt)return true // Clock correction must not postpone indefinitely.
    return (lastSuccess<=0 || now-lastSuccess>=WEEK_MS) && (lastAttempt<=0 || now-lastAttempt>=RETRY_MS)
}


When now < lastSuccess (e.g., system clock moved backward after a prior successful check) and onResume triggers check(), check() overwrites attempt = now (UpdateMonitor.kt line 39; UpdateMonitor.swift line 29), but success is only updated inside the try block after both network requests succeed. If that check fails (e.g., device is offline), lastSuccess remains in the future (now < lastSuccess). On every subsequent onResume() call (every time the app returns to foreground or the timer fires), if (now < lastSuccess || now < lastAttempt) return true short-circuits to true before checking now - lastAttempt >= RETRY_MS, violating the documented 1-hour retry policy ("Failed due checks retry after one hour while the process runs").

Smallest Fix: Normalize future timestamps to 0 before evaluating the standard backoff predicates in UpdatePolicy.due:

fun due(now:Long,lastSuccess:Long,lastAttempt:Long):Boolean {

    return (s<=0 || now-s>=WEEK_MS) && (a<=0 || now-a>=RETRY_MS)
}


With this change, a backward clock shift resets s to 0 (triggering an immediate check if a was also in the future or
