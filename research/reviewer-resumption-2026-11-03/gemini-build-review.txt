3. Concrete New Defects in Build, Packaging & Reproduction Files
[B-01] Validation Coverage Gap: --strict in README.md/BUILD.md Bypasses Default Batched verify() and Its Custom KV Rollback

Severity: Medium / High

File / Line: README.md:31-32, BUILD.md:9-11, core.cpp:147-204, 242.

Trigger Condition: Following the reproduction commands in README.md (check-native.py ... --strict) or relying on the 31 checks in BUILD.md. When strict=true is passed, core.cpp:242 routes verification to verify_serial() (which uses sync(prefix) and single-token decode). However, default callers omitting "strict": true execute verify() (core.cpp:170-204), which uses a separate, hand-written KV rollback loop (before, llama_memory_seq_rm, and batched decode(batch, true)) and omits "verification_mode" from its JSON response (core.cpp:202 vs 168).

Minimal Confirmation Test: Send {"op":"verify","prefix":[...],"proposal":[...]} without "strict" via nl_call: inspect the returned JSON to confirm "verification_mode" is absent and that cached retains rejected proposal tokens until the next sync()/verify() call.

Minimal Fix:

Add {"verification_mode", "batch"} to the return object of Engine::verify() at core.cpp:203.

Run check-native.py both with and without --strict in README.md / BUILD.md so the batched KV rollback path (core.cpp:178-186) is explicitly covered by correctness checks.

[B-02] Global Symbol Table Pollution & sha256_* Symbol Collision Hazard in libnodelift

Severity: Medium

File / Line: CMakeLists.txt:4, 6, 25, 30; core.h:4-11; core.cpp:4-6.

Trigger Condition: CMakeLists.txt builds llama statically with PIC (BUILD_SHARED_LIBS OFF, CMAKE_POSITION_INDEPENDENT_CODE ON) and links it alongside ${LLAMA_SOURCE_DIR}/vendor/hash/sha256/sha256.c into the shared library nodelift without setting hidden symbol visibility (CMAKE_C_VISIBILITY_PRESET hidden, CMAKE_CXX_VISIBILITY_PRESET hidden) or a linker export list. As a result, libnodelift.dylib / libnodelift.so exports not only the 5 nl_* C ABI functions, but also all GGML_API / LLAMA_API symbols and the unprefixed global C symbols sha256_init, sha256_update, and sha256_final. Loading libnodelift into a host process (Python, Android JNI process, or LM Studio) that links another llama.cpp build or a C library defining sha256_init/sha256_update/sha256_final risks symbol interposition or ODR violations.

Minimal Confirmation Test: Inspect exported global symbols on the built library using nm -gU build-nodelift/lib/libnodelift.dylib (macOS) or nm -D libnodelift.so (Linux/Android): verify that  _sha256_init, _sha256_update, _sha256_final, _llama_*, and _ggml_* are globally exported alongside _nl_*.

Minimal Fix:
In CMakeLists.txt, set hidden visibility on nodelift and restrict exported symbols to _nl_*:

CMake
set_target_properties(nodelift PROPERTIES
  C_VISIBILITY_PRESET hidden
  CXX_VISIBILITY_PRESET hidden
  VISIBILITY_INLINES_HIDDEN ON)


And mark the 5 functions in core.h / core.cpp with __attribute__((visibility("default"))) (or pass -Wl,-exported_symbols_list on Apple platforms).

[B-03] Missing core.h in nodelift Target Sources Breaks iOS .framework Header Installation

Severity: Medium (for iOS builds)

File / Line: CMakeLists.txt:25, 36-41.

Trigger Condition: Configuring CMake with -DCMAKE_SYSTEM_NAME=iOS. Lines 36–41 set FRAMEWORK TRUE and PUBLIC_HEADER core.h on target nodelift. However, in CMake, files listed in PUBLIC_HEADER must also be listed as sources of the target (add_library or target_sources) for CMake's framework generator to copy them into nodelift.framework/Headers/. Because line 25 (add_library(nodelift SHARED core.cpp "${LLAMA_SOURCE_DIR}/vendor/hash/sha256/sha256.c")) omits core.h, CMake does not populate Headers/core.h inside the framework bundle.

Minimal Confirmation Test: Configure and build with -DCMAKE_SYSTEM_NAME=iOS and inspect build/lib/nodelift.framework/Headers/core.h (file will be missing).

Minimal Fix: Add core.h to the target sources in CMakeLists.txt:25:

CMake
add_library(nodelift SHARED core.cpp core.h "${LLAMA_SOURCE_DIR}/vendor/hash/sha256/sha256.c")

[B-05] CMakeLists.txt Missing CMAKE_CXX_STANDARD_REQUIRED ON and Subdirectory Scope of Android -O3 Flag

Severity: Low

File / Line: CMakeLists.txt:3, 16-19, 23.

Trigger Condition:

Line 3 sets set(CMAKE_CXX_STANDARD 17) without set(CMAKE_CXX_STANDARD_REQUIRED ON) or set(CMAKE_CXX_EXTENSIONS OFF).

Lines 17–19 call add_compile_options("$<$<CONFIG:Debug>:-O3>") before add_subdirectory("${LLAMA_SOURCE_DIR}" llama). Because Debug builds in CMake do not define NDEBUG, compiling ggml and llama in Debug mode with -O3 keeps runtime assert() / GGML_ASSERT() checks active inside compute paths while mixing -O0 (from toolchain CMAKE_CXX_FLAGS_DEBUG) and -O3 on the command line.

Minimal Confirmation Test: Inspect compile_commands.json generated with -DCMAKE_BUILD_TYPE=Debug -DANDROID=ON: verify that -O0 and -O3 both appear on the compiler line without -DNDEBUG.

Minimal Fix: Add set(CMAKE_CXX_STANDARD_REQUIRED ON) after line 3, and document or use RelWithDebInfo instead of mutating Debug flags globally across subdirectories.
